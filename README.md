# Toxoplasma gondii: QSAR & Molecular Docking Pipeline

![Python](https://img.shields.io/badge/Python-3.11-blue?style=for-the-badge&logo=python)
![Status](https://img.shields.io/badge/Status-Reproducible-success?style=for-the-badge)

> Computational pipeline comparing classical Machine Learning (stacking ensembles) against a Graph Neural Network (ChemProp D-MPNN) for QSAR modeling of *TgDHFR* inhibitors, followed by ADMET profiling and structure-based virtual screening / molecular docking (AutoDock Vina) against PDB 6AOG.

This README documents how to reproduce every computational result in the manuscript, including expected runtimes, hardware assumptions, and known sources of numerical variation. It reflects the environment and pipeline as validated on 2026-09-21/23 (see "Reproducibility notes" below).

---

## 1. Repository structure

```
scripts/                 Pipeline steps (00 through 19), project modules (paths_config.py, logger_utils.py, nb_stats.py, gnn_utils.py)
scripts/qsartools/       Reusable, tested QSAR tools (featurization, splits, models, statistics, ...); tests in tests/qsartools/
scripts/tf/              Steps that need the separate TensorFlow environment (reproduction of the original DNN)
run_pipeline.py           Orchestrator: runs all steps in order, or a subset (see below)
conda_environment.yml     Conda environment definition (Python 3.11, pip-managed dependencies)
requirements.txt          Pinned pip dependencies (see comments inside for rationale)
setup_env.sh              One-shot environment setup script
data/                     Input datasets (SMILES/pIC50 training set, TDC hERG/Caco-2 tables, FDA library)
receptor/                 Prepared receptor and crystal ligand (PDBQT) for docking
results/                  CSV/NPY/joblib outputs generated by the pipeline (git-tracked for auditability)
figures/                  PNG/PDF figures generated by the pipeline
latex/                    Auto-exported LaTeX \newcommand variable files, consumed by the manuscript
logs/                     Per-script logs plus a master_pipeline_<timestamp>.log for each full/partial run
```

`results/`, `figures/`, `logs/` and `latex/*.tex` are committed to the repository so that reviewers can inspect the exact outputs of the validated run without re-executing the pipeline, while still being able to regenerate them from scratch (see Section 4).

## 2. Environment setup

The pipeline was validated on Python 3.11.16 (Linux, 48 CPU threads, 248 GB RAM). It should run on fewer cores, at a proportionally longer runtime (see Section 5).

```bash
conda env create -f conda_environment.yml -n mlvsgnn_repro
bash setup_env.sh
```

`setup_env.sh` creates/updates the conda environment from `conda_environment.yml` (which in turn installs everything pinned in `requirements.txt`), then installs `PyTDC==0.4.1` separately with `pip install --no-deps` — PyTDC declares an old `rdkit-pypi` build as a dependency that would silently downgrade/duplicate the pinned RDKit if installed normally — and finally runs `python run_pipeline.py --check` to confirm every third-party module actually imports.

Key pinned versions (full list and rationale in `requirements.txt`; the complete resolved environment, including transitive dependencies, is captured in `requirements-lock.txt` via `pip freeze` on the validated workstation):

| Library | Version | Notes |
| :--- | :--- | :--- |
| RDKit | 2025.9.3 | Single installation; verify with `pip list \| grep -i rdkit` after setup (PyTDC must not add a second one) |
| scikit-learn | 1.6.0 | Classical ML / stacking ensembles |
| XGBoost / LightGBM | 3.1.2 / 4.6.0 | Stacking base learners |
| PyTorch / Lightning | 2.5.1 / 2.6.5 | ChemProp backend (CPU only in this configuration) |
| ChemProp | 2.2.4 | D-MPNN GNN baseline (v2 API) |
| AutoDock Vina (Python bindings) | 1.2.7 | Molecular docking |
| Meeko / Gemmi | 0.8.0 / 0.7.5 | PDBQT ligand preparation (Meeko requires Gemmi at import time even though it is not declared as a dependency) |
| PyTDC | 0.4.1 | ADMET oracles (hERG, Caco-2); installed with `--no-deps`, see above |

**Not used / intentionally removed:** DGL, DGL-LifeSci and the AttentiveFP baseline were removed from this pipeline. DGL 2.1.0 (the last version with prebuilt wheels at the time of writing) does not support PyTorch 2.5.1, and there is no compatible combination that also satisfies ChemProp's requirements. ChemProp (D-MPNN) is the only GNN baseline reported.

**System dependency (optional):** `obabel` (OpenBabel) is only required by `scripts/prep_receptor.py`, which is **not** part of the `run_pipeline.py` sequence. It is only needed if you want to regenerate `receptor/receptor.pdbqt` and `receptor/crystal_ligand.pdbqt` from the raw PDB structure. Since both prepared files are already tracked in `receptor/`, most users will not need to install it.

```bash
sudo apt-get update && sudo apt-get install openbabel libxrender1 libxext6   # only for prep_receptor.py
```

## 3. Running the pipeline

```bash
python run_pipeline.py --list            # show all 32 steps in execution order, with what each cost on this machine
python run_pipeline.py --check           # verify every dependency actually imports (no computation)
python run_pipeline.py                   # run everything: main analysis (00 -> 09), outlier sensitivity (S01, S02, 10), scaffold-split robustness (SC01, SC09, 13), then the figure stage
python run_pipeline.py --from 05         # resume from step 05 onward (e.g. after an interruption)
python run_pipeline.py --only 07 07.1    # run only the listed steps
python run_pipeline.py --no-sensitivity  # skip the with-extreme-values re-run
python run_pipeline.py --no-scaffold     # skip the scaffold-split re-run (SC01, SC09, 13)
python run_pipeline.py --only figures    # rebuild every figure and table from existing results (seconds, no recomputation)
python run_pipeline.py --quick           # reduced smoke run of the WHOLE pipeline, written to quick_run/ (see below)
```

`--quick` is for checking that the pipeline runs end to end without waiting days for it. It selects the `quick`
hardware profile (one outer repeat instead of five, a 3-fold inner loop, 50 trees, 5 y-randomization permutations, 2
ensemble runs) while keeping all four representations, so every figure, table and LaTeX variable is still produced.
**Its numbers are not the published ones**, and for that reason it redirects every output -- results, figures, LaTeX
variables and logs -- to `quick_run/`, where it cannot overwrite a real run. Set `MLGNN_OUT_DIR` to send them
somewhere else.

The TensorFlow steps (15, 16, 17, SC17) run under a separate interpreter, because TensorFlow is not part of the main
environment. Point `MLGNN_TF_PYTHON` at it; a full run stops immediately, before computing anything, if it is missing:

```bash
export MLGNN_TF_PYTHON=/path/to/tf-env/bin/python   # see requirements-tf-lock.txt
```

Each run writes a master log to `logs/master_pipeline_<timestamp>.log` in addition to each script's own `logs/<script>.log`. On a non-zero exit code the pipeline halts immediately; re-run with `--from <step>` after fixing the issue rather than restarting from scratch.

For long unattended runs (e.g. over SSH), use `tmux` or `nohup` — step 01 alone takes on the order of hours (see below).

Hardware profile and parallelism are controlled via environment variables read by `scripts/paths_config.py`:

```bash
export MLGNN_PROFILE=workstation   # default; see paths_config.py for available profiles
export MLGNN_N_JOBS=8              # override the number of threads (default: min(profile setting, os.cpu_count()))
```

## 4. Expected runtime (validated hardware: 48 threads / 248 GB RAM)

`python run_pipeline.py --list` prints every step with the wall-clock time of its last run **on your machine**, read
from the step logs, so the numbers below do not have to be kept in sync by hand. Note that a step which resumed from a
checkpoint, or which only re-summarized existing results, is listed with the seconds it took that time, not with its
from-scratch cost.

The pipeline is dominated by a handful of steps. Measured here, from scratch:

| Step | Description | Approx. time |
| :--- | :--- | :--- |
| 01 | Nested CV, 4 representations x 25 outer folds, 41 stacking candidates per inner loop | ~46 h |
| S01 | Step 01 re-run on the set that keeps the 2 extreme pIC50 values (`sensitivity/`) | ~57 h |
| SC01 | Step 01 on scaffold-grouped outer folds (`scaffold/`) | ~56 h |
| 03 | Y-randomization, 4 tests x 100 permutations, selection repeated inside every permutation | ~19 h |
| 12 | D-MPNN with a hyperparameter search inside every outer fold | ~15 h of worker time |
| SC19 | Pretrained graph networks (CheMeleon, D-MPNN ensemble) on scaffold folds | ~12 h |
| 16, 17, SC17 | TensorFlow audit of the original network (leakage ladder, nested CV) | ~1.5 h each |
| 09, SC09, 15 | Default D-MPNN (random and scaffold folds), verbatim re-run of the original notebooks | ~1.3 h each |
| 04 | Feature selection (Exp B) and Gaussian augmentation (Exp C) | ~70 min |
| 00, 02, 05-08, 10, 13, 14, 18, 19, figures, 11 | Everything else: screening, docking, ADMET, summaries, figures and the manuscript check | seconds to minutes |

**A full run from a clean state is on the order of 8-9 days of wall-clock time** on this hardware. Steps 01 and 03
checkpoint every result as it is produced and resume where they left off, so an interruption costs only the work in
flight. Use `tmux` or `nohup` for unattended runs, and `--quick` (above) when the point is to verify that the pipeline
executes rather than to reproduce the numbers.

Step 04 can look "stuck" for several minutes with no console output during Experiment B (single-threaded by design,
see below); this is expected, not a hang.

## 5. Reproducibility notes

Every step uses a fixed random seed (`RANDOM_STATE = 42` in `paths_config.py`, propagated to scikit-learn, XGBoost, LightGBM, PyTorch/Lightning `seed_everything`, and AutoDock Vina's `seed` parameter). Despite this, a small amount of run-to-run numerical variation is expected and has been characterized empirically:

- **Step 04 (baseline, feature selection, augmentation):** every model of this step is fitted single-threaded and the parallelism is applied across independent tasks (features in the permutation importance, runs of the 5-run ensemble), so the results do not depend on the number of workers. The cause of the earlier run-to-run differences was identified: a multi-threaded `RandomForest.predict()` sums the trees in a thread-dependent order, which changes the last bits of the predictions, and the old selection rule `importance > 0` then flipped the ~750 features whose importance is zero up to floating-point noise (about 1e-15; the smallest genuine importances are about 1e-7). Two executions of the old code retained 1389 and 1826 bits of the same split. The selection now keeps features with importance above `IMPORTANCE_TOL = 1e-9` and the fits use `n_jobs=1`; permutation importances computed with 46 and with 8 workers were bitwise identical and retained the same 1255 bits.
- **Ensemble of runs (step 04):** the 5 runs of the ensemble now use different seeds for the tree ensembles (`RANDOM_STATE + run`). Previously the reseeding was never applied (the stacking object has no `random_state`), so the 5 runs were identical copies.
- **Redocking validation (step 06) and docking (step 07):** deterministic given the fixed Vina seed (42); centroid distance for the redocking control reproduced at 0.317 Å (threshold: 2.0 Å) across repeated runs.
- **ChemProp / GNN (steps 09, 12, 19 and their scaffold counterparts):** PyTorch/Lightning training on CPU with multiple threads is not bit-reproducible even with a fixed seed, for the same floating-point non-associativity reason as above. Repeated 5x5 CV runs agree to about the third decimal rather than to the last one: the mean fold R² of the default D-MPNN has been 0.7248, 0.7213 and 0.7249 across executions of the same code on the same folds. Expect the third decimal of any neural result to move; the classical steps do not move at all.
- **Everything else is deterministic.** Re-running the pipeline end to end reproduces the classical results exactly, because the outer folds come from a fixed seed, the preprocessing and the architecture search live inside each fold, and the fits that could depend on thread scheduling are single-threaded. The published LaTeX variables of steps 01-08 and 10-13 are therefore reproducible bit for bit; only the neural ones are not.

If you reproduce this pipeline on different hardware, expect small variation in the GNN's R², but not in the qualitative conclusions reported in the manuscript.

## 7. Docking setup

Docking targets the DHFR active site of PDB 6AOG. The screening box is centered on chain B specifically (not the average of both chains, which was found during redocking validation to be offset from the true active site — see `latex/redocking_variables.tex` and the `[IMPORTANT WARNING]` printed by `scripts/06_redocking_validation.py`). `CENTER_X/Y/Z` in `paths_config.py` must match the value step 06 reports; the pipeline checks this consistency automatically and reports the offset (validated at 0.001 Å).

## 9. Numbers in the manuscript: where they come from and how to use them

Every number the paper states is a `\newcommand` that the pipeline writes, never a literal. Two things follow, and
they are the point of the whole arrangement:

- **Re-running a step updates the text.** No sentence has to be edited after a run, and none can be forgotten.
- **Rewording a sentence cannot change a value.** The prose is yours to rewrite freely: change a term, reorder a
  paragraph, rephrase a claim. The macro travels with the sentence and no test will stop you.

### 9.1 Where to look: `MACROS.md`

[`MACROS.md`](MACROS.md) is the generated index of every exported value. It opens with a table of the 18 families, each
with its macro prefixes, how many values it holds, how many the manuscript already cites, and its step. Then one
section per family, listing every macro with:

| Column | What it tells you |
| --- | --- |
| Macro | the name to write in the `.tex` |
| Current value | what it holds after the last run of its step |
| Cited in | the section files that already use it, or `—` when nothing does |
| Note | why it might be worth citing, taken from `macro_notes.csv` |

The pipeline exports about 1430 values and the manuscript cites about 390. **The rest are not a backlog.** They are
there so that a referee's objection can be answered by looking a number up instead of recomputing it. Search the file
by topic through the prefixes (`Screen*` for the screening, `NB*` for the paired comparisons, `Scaffold*` for the
scaffold-grouped re-run, and so on), or by the family titles in the index.

### 9.2 How to propose a value for the text

Add a row to [`macro_notes.csv`](macro_notes.csv) with the macro and one sentence on why it belongs in the paper:

```csv
macro,note
YRandomPassed,"Verdict of the y-randomization test as a single value; the text never states it"
```

The note appears in the catalogue beside the value the next time step 11 runs, so a suggestion is visible to everyone
and survives regeneration. **Never edit `MACROS.md`**: it is overwritten.

### 9.3 How to write a value into a section

Write the macro, not the number: `the ensemble reached $R^2 = \MorganRTwoMean$`, not `0.807`. Then run
`python run_pipeline.py --only 11`, which fails if the macro does not exist. If the value you need has no macro, it
has to be exported by the step that measures it rather than typed into the text; a setting rather than a measurement
belongs in step 00.1 (`scripts/00.1_export_config.py`).

### 9.4 How to regenerate a family, and what else to refresh

Each family's section in `MACROS.md` carries its own command, and the dependencies between steps, which the catalogue
derives from the code:

```
`paper_variables.tex`, written by `01_nested_cv_stacking.py`. Regenerate with `--only 01`.
Step(s) 01.1, 02, 09, 09.1, 12, 13, 18, 19 read what it writes, so refresh those after it.
```

So a partial re-run is never guessed at: the family tells you which steps consume its output and which it consumes.
Step 11 is always last, because it rewrites the catalogue and checks the manuscript. The dependency lines see only
direct uses of a path constant, so they can understate a dependency but never invent one.

### 9.5 What the tests enforce

`pytest tests/` fails when:

- a macro disagrees with the code behind it (`tests/test_manuscript_constants.py`), for every setting the text states;
- a value that has a macro is also written as a literal in a section, which is how a hand-written number used to get in;
- `MACROS.md` drifts from `latex/`, which also catches a macro file regenerated on its own while the rest stayed behind;
- a row of `macro_notes.csv` names a macro no step exports, or carries no note;
- a macro file has no title in [`macro_families.csv`](macro_families.csv), or names a step that is not in the pipeline.

The one thing no test can judge is whether the prose around a correct number still says the right thing. That remains
a reading job.

### 9.6 Building with the right checks

`./build.sh` asks what changed before compiling and runs only the checks that can catch it:

```
What changed since the last build?
  1) prose only          - the manuscript checks, 6 s
  2) code or settings    - the whole test suite, 40 s
  3) I re-ran a step     - refresh the catalogue, then the whole suite
  4) nothing, just build - no checks
```

A failing check stops the build and prints the test that failed, so a PDF is never produced from a manuscript that
contradicts the results. The same choices are available without the question, which is what a hook or another script
should use:

| Command | What it does |
| --- | --- |
| `./build.sh` | asks, then compiles every document |
| `./build.sh --prose` | the manuscript checks, then every document |
| `./build.sh --code` | the whole test suite, then every document |
| `./build.sh --step` | refreshes the macro catalogue, the whole suite, then every document |
| `./build.sh --no-checks` | straight to compiling |
| `./build.sh paper_reading` | that document alone, no checks |

The question is asked only when a terminal is attached and no document and no flag were given, so every scripted use
keeps compiling exactly as before. Committing and pushing are deliberately not part of this: the script builds.

**The supplement is built first**, because the manuscripts resolve its table and figure numbers by reading its `.aux`
through `xr-hyper`: the text writes `Table~\ref{S-tab:ad_sensitivity}`, never `Table~S10`, so inserting a table
renumbers the references by itself. A test refuses a hand-written `Table~S<n>`, checks that every `S-` label exists in
the supplement, and checks that each manuscript loads the package; if the `.aux` is missing the references print as
`??` and the build reports them as undefined, so the failure is loud.
